# ADR-001 — Laravel modular monolith

Status: Accepted

Owner: Engineering + Product

Decision date: 2026-10-16

## الاعتماد المسجل

اعتمد Ibrahim الخيار التصميمي Structured Laravel Modular Monolith بصفته Product Owner وفق الموافقة السابقة، وبصفته Lead Developer / Engineering Decision Authority وفق موافقته الصريحة بتاريخ 2026-10-16. هاتان موافقتان للشخص نفسه بدورين مخولين، لا لشخصين مستقلين. يشمل القبول ملكية modules وعقود Application المحددة النطاق والأحداث الموثوقة بعد commit والمفاضلات المعمارية الموثقة، ولا يعتمد runtime/package/DB/queue/cache/hosting أو أي سياسة OPEN أو تنفيذ. [سجل الموافقتين ومصدرهما وحدودهما](../../governance/decision-approvals/ADR-001.md). تبقى التوصيات والحقائق التاريخية أدناه في سياقها الأصلي؛ لا تعني تحقق التنفيذ أو تشغيل الخدمات.

## نطاق القرار والحقائق المؤكدة

- أكد المستخدم اختيار Laravel، كما أكد تفضيل **package-first** كمنهج تقييم: فحص إمكانات Laravel/first-party أو package ناضجة قبل إعادة بناء وظائف عامة. لا يفرض هذا التفضيل استخدام package، ولا يختار واحدة، ولا يعتمد runtime بعينه.
- يوصي PRD بـmodular monolith، لكن المعمارية وإصدارات Laravel/PHP ومحرك قاعدة البيانات والـqueue والاستضافة والحزم ما تزال Proposed أو OPEN.
- تشمل قيود المنتج التي يستند إليها هذا التقييم نظاماً داخلياً لشركة واحدة، وفرض authorization وrecord/field scope على الخادم، وموافقات قابلة للتدقيق وsegregation of duties (SoD)، وسجلات مخزون ومالية غير قابلة للتعديل الصامت أو قابلة للتصحيح عبر reversal، وtransactional outbox، وقواعد stock/accounting حتمية. لا تحسم هذه القيود سياسات الأعمال المفتوحة.
- لم يُعثر في المستودع وقت الفحص على `composer.json` أو `composer.lock` أو `artisan` أو Laravel application scaffold. نتيجة فحص runtime موضحة أدناه؛ ولا يمنح هذا ADR إذناً بإنشاء تطبيق أو تثبيت package أو تنفيذ سياسة أعمال.

## الخيارات المقارنة

| الخيار | الملاءمة والفوائد | التكاليف والمخاطر والنتيجة |
|---|---|---|
| **Structured Laravel modular monolith** — تطبيق/deployment واحد مع ownership وعقود domain صريحة؛ ويمكن تشغيل workers كعمليات منفصلة من codebase نفسه. | الأنسب حالياً لنطاق الشركة الواحدة في PRD ولسير العمل الذي يحتاج قرارات فورية داخل transaction. يقرب process واحد وحدود transaction علائقية authorization وSoD وstock وfinance وaudit وoutbox، ويسهّل اختبارها. ويمكن استخدام منظومة Laravel packages خلف adapters دون جعل package هي domain model. | يحتاج فرض ownership على modules وقواعد dependencies واختبارات boundaries؛ وقد تظل قاعدة البيانات/schema المشتركة وglobal framework boot مصدراً للترابط. وجود مجلدات بأسماء modules لا يجعل monolith modular. كما أن deployment واحداً قد يصبح وحدة عطل أو توسع مشتركة. |
| **Unstructured monolith** — نماذج وخدمات application مشتركة مع وصول متبادل غير منضبط بين الخصائص. | أقل كلفة تنظيمية في البداية، وسريع لـproof of concept صغير. | قد تتجاوز الكتابات بين modules وعلاقات Eloquent العامة ومنطق permissions حدود ownership وscope. يزيد الترابط كلفة الاختبار والتغيير، خصوصاً حول SoD وfinance/stock وaudit/outbox. لا يحقق ميزة تشغيلية مهمة مقارنة بـmodular monolith منضبط، ويضعف إمكانية الاستخراج لاحقاً. غير موصى به. |
| **Microservices** — خدمات مستقلة النشر بعقود شبكية وعمليات/بيانات مستقلة. | قد يناسب فرقاً ذات ownership مستقل أو cadence نشر أو احتياجات توسع/عزل أعطال مثبتة بالأدلة. | يضيف أعطال الشبكة وهوية service وauthorization ومراقبة موزعة وإعادة المحاولة وتكرار البيانات ومشكلات الاتساق بين الخدمات قبل وجود دليل على الحاجة. لا يمكن الاعتماد على network call أو eventual consistency وحدهما لضمان stock availability أو posted journals أو SoD أو outbox/audit. كما يزيد كلفة التشغيل والاستعادة بما لا يلائم خط الأساس الحالي لشركة واحدة. غير موصى به كبداية؛ يعاد النظر فيه عند ظهور أدلة تشغيلية/تنظيمية ووجود خطة انتقال صريحة. |

هذه مقارنة معمارية نوعية وليست benchmark للأداء. لا تتوفر أدلة عن حمل الإنتاج أو staffing أو deployment أو failure injection تبرر درجات رقمية.

## التوصية المقترحة

**التوصية هي structured Laravel modular monolith** بدلاً من unstructured monolith أو تقسيم أولي إلى microservices. يبدأ النظام بتطبيق واحد قابل للنشر وقاعدة علائقية مختارة لاحقاً؛ محرك القاعدة ينتظر ADR-002. يمكن تشغيل queue consumers كعمليات تشغيلية منفصلة عند الحاجة باستخدام codebase نفسه؛ وهذا لا ينشئ domain service مستقلاً ولا يختار منتج queue. يجب أن تكون حدود modules حقيقية وقابلة للاختبار مع إبقاء إمكانية الاستخراج مستقبلاً دون الادعاء بأنه مجاني.

قبول **الخيار المعماري** يتطلب مراجعة موثقة من Engineering + Product لخريطة ownership وحدود modules؛ ولا يتطلب إنجاز runtime/database proof قبل اعتماد هذا الخيار. إثبات runtime وقاعدة البيانات متطلب لاحق مستقل قبل الأعمال التي تعتمد عليه، وفق بوابات المهام وADRs المعنية. المراجعة لا تقبل أي سياسة PRD `OPEN-*`، ولا تختار الاستضافة أو package، ولا ترفع حجب scaffold أو implementation.

## بنية modules وlayers المقترحة

تُستخدم ممارسة الهندسة الحالية كنقطة بداية، لا كادعاء بوجود code:

```text
app/Modules/{Module}/
  Domain/          # owned invariants and domain types; no Laravel facade/provider SDK
  Application/     # use cases, authorization/context checks, typed ports and transaction boundary
  Infrastructure/  # owned persistence, Laravel adapters, queue/provider integrations
  Presentation/    # HTTP/request/response adapters and module-facing entry points
  Providers/       # Laravel composition/registration seam, if needed

tests/Unit/
tests/Feature/
tests/Contract/
```

لكل aggregate مالك واحد للكتابة كما يحدد module catalog. Controllers وjobs adapters وليست مالكاً بديلاً لقواعد الأعمال. تفرض policies وscoped queries صلاحيات object/field في كل نقطة دخول؛ وتظل application use cases وdomain guards مسؤولة عن التحقق من سياق الصلاحية وانتقالات الحالة. يجب ألا يعتمد Domain على Laravel facades أو Eloquent models من module آخر أو vendor SDK. تُحصر Shared Kernel في أنواع صغيرة مثل IDs وclock وmoney/correlation primitives، ولا تتحول إلى business models مشتركة.

تتم الاستدعاءات بين modules عبر typed application contracts واضحة تتضمن entity/scope وexpected-version. يكتب كل module aggregates التي يملكها فقط. تستخدم contracts متزامنة عندما يحتاج المستدعي نتيجة حتمية فورية، وتستخدم أحداث ما بعد commit للآثار اللاحقة وprojections. تكون القراءة العابرة عبر scoped query contracts أو projections يملكها القارئ، لا عبر shared mutable models أو كتابة مباشرة في جداول module آخر. تُمنع dependencies الدائرية ويُختبر dependency graph.

## تكامل package-first وحدود service providers

package-first **منهج للاختيار**، وليس «package لكل module» ولا إذناً تلقائياً بتثبيت dependencies. تُفحص أولاً capability مدعومة من Laravel/first-party أو package خارجية ناضجة للوظائف العامة، بعد التحقق من توافق PHP/Laravel/database المستهدف، والدعم/EOL، والرخصة، والأمن وسلسلة التوريد، وmigrations، وكلفة التشغيل، والاختبارات، وlock-in، ومسار الاستبدال. تبقى authorization وSoD وworkflow وfinancial/stock invariants وaudit وملكية البيانات قواعد domain/application يملكها النظام. عند ملاءمة ذلك يستخدم النمط الهجين: آلية package ← adapter/port ضيق ← policy واختبارات يملكها Arasya. وثيقة package strategy قائمة مراجعة للمرشحين وليست دليلاً على توافق أي مرشح أو اعتماده.

**الحد المقترح:** يُعرّف port عند حدود module المستهلك/المالك، ويوضع adapter في Infrastructure لذلك module أو في integration module ذي ownership صريح، ثم يربط عند application composition root. يجوز لـmodule service provider تسجيل bindings الخاصة به وما يلزم من routes/listeners/configuration وقت boot فقط. لا توضع قرارات domain أو استدعاءات الشبكة إلى providers داخل boot، ولا تصبح model أو facade أو schema أو role لحزمة vendor هي العقد التجاري المعتمد. تبقى معرفات provider خارجية وثانوية مقابل معرفات النظام الثابتة.

توضح وثائق Laravel 13 الرسمية أن service providers موضع bootstrap/composition للتطبيق، وتفصل container bindings في `register()` عن routes/listeners وبقية التسجيل في `boot()`، وتسجل providers التطبيق مركزياً. لذلك، إذا اختير Laravel 13، يكون التسجيل الداخلي الصريح لـmodule providers في جذر التطبيق (`bootstrap/providers.php`) مع بقاء ownership محلياً. يجب تأكيد آلية التسجيل الفعلية للإصدار الذي سيُختار؛ فهي غير محسومة هنا. تُراجع آلية package auto-discovery وإعداداتها قبل تفعيلها. تبدأ domain modules كـnamespaces/directories داخل التطبيق الواحد، لا كـComposer packages منفصلة. ولا يُحوّل module إلى Composer package داخلي إلا إذا بررت ذلك عقود مستقرة وملكية واضحة لـmigrations/configuration واتجاه dependencies واختبارات/إصدارات وحاجة فعلية لإعادة الاستخدام أو العزل.

## حدود حرجة لا تحسمها packages أو events

| الحد | الإنفاذ المقترح والاعتماد غير المحسوم |
|---|---|
| **SoD / approvals** | يملك Workflow الطلبات والسياسات والتاريخ؛ ويتحقق module مالك aggregate الحساس من actor والموضوع والكيان والمبلغ/version والانتقال الموافق عليه عند تنفيذ mutation. يُمنع self-approval حيث تقتضي القاعدة، ولا يُفترض استثناء Super Admin. لا تكفي role/approval package أو حالة UI. تظل thresholds والاستثناءات وbreak-glass مفتوحة في OPEN-02 بانتظار اعتماد Executive. |
| **Audit وoutbox** | يُحفظ business change وoutbox event وaudit intent المطلوب في transaction قاعدة البيانات نفسها. لا يتم النشر إلا بعد commit؛ ويُفترض at-least-once delivery؛ ويكون consumer idempotent عبر inbox/dedup record تحفظ مع أثره. لا يوجد exactly-once عبر الشبكة. ولا تثبت event/audit package عامة atomicity أو الاكتمال أو retention أو redaction أو tamper resistance. |
| **Finance وstock** | يملك Sales الطلبات التجارية؛ ويملك Inventory الحجوزات وon-hand وحركات stock؛ ويملك Finance القيود والترحيل والعكس. لا يؤدي اعتماد quote/order وحده إلى صرف فعلي أو الاعتراف بالإيراد. إذا تطلب use case نتيجة stock/ledger ذرية فعلاً، فيمكنه تنسيق contracts المالكين بصورة متزامنة داخل transaction محددة على المحرك العلائقي المختار، مع بقاء كتابة كل module لجداوله فقط. يجب تحديد lock order والتكرار والفشل/rollback والتسوية وإثباتها على المحرك المختار. وإذا سمحت سياسة الأعمال بإتمام غير متزامن، فتمثل حالة الانتظار والتسوية/التعويض صراحة؛ ولا يُدّعى أن eventual consistency تحفظ stock limits أو journal متوازناً ومرحلّاً. تظل قواعد accounting trigger وvaluation والتعاريف المرتبطة مفتوحة في OPEN-03/04/05، وتتطلب قرار Finance/Warehouse/Operations قبل التنفيذ المعني. |
| **Scope والبيانات الحساسة** | يفرض tenant/entity/record/field scope في queries وAPIs وjobs وsearch وnotifications وexports والوصول إلى documents الخاصة. لا تعوض packages أو إخفاءات presentation عن اختبارات server-side policies. |

## استراتيجية الاختبار والتحقق

يجب أن تختبر أي implementation لاحقة المعمارية نفسها، لا classes منفردة فقط:

1. **Architecture/boundary checks:** إثبات اتجاه dependencies المسموح بين modules، وغياب الدورات واعتماد Domain على framework/vendor، ومنع الكتابة إلى models/tables مملوكة لغيره، وإبقاء Shared Kernel صغيراً. تُختبر ملكية providers/routes وbindings عند composition root.
2. **Domain and application tests:** انتقالات الحالة وسياق authorization وحالات SoD/self-approval السلبية وتعارض expected-version وidempotency وقواعد عدم التعديل/reversal وسلوك typed contracts بين modules. لا تثبت unit tests وحدها معاملات قاعدة البيانات.
3. **Laravel feature/contract tests:** تفرض الطلبات المصادق عليها ونقاط دخول background jobs record/field scope؛ وتملك package adapters وعقود modules contract tests؛ وتفشل permissions بشكل مغلق. تُختبر events/outbox وفشل providers وإعادة المحاولة.
4. **Database integration/concurrency tests:** على المحرك المحدد في ADR-002، لإثبات ذرية outbox مع aggregate، وinbox deduplication، وتزامن حجز/صرف stock، واتزان journal وposting/reversal، وترتيب الأقفال وrollback والاستعادة. لا يُعد in-memory أو محرك مختلف دليلاً على locking في الإنتاج.
5. **Cross-module acceptance slices:** تربط بالسيناريوهات المناسبة في PRD، ومنها AT-03/04/07/08/14/15. وتتحقق من عدم تحريك stock أو revenue عند اعتماد quote، ومن أثر صرف واحد مع retries، ومن منع self-approval حيث يلزم، ومن صلاحية السجلات وتسويتها. تضاف اختبارات الخصوصية لـAT-01 وفشل التشغيل لـAT-11 مع وصول الوحدات المعنية.
6. **Package/runtime checks:** حل dependency set المحددة على PHP/Laravel المختارين؛ ومراجعة Composer metadata/transitives والرخص/advisories وmigrations ومسار الاستبدال؛ ثم تشغيل static analysis وformatting واختبارات feature/contract/security/concurrency وmigrations forward/recovery وتجربة upgrade وفق ما يعتمد. لا يثبت README أو upstream tests توافق التطبيق.

لم يُشغّل لهذا ADR أي package resolution أو application أو module-boundary test أو migration أو runtime integration test من Laravel. ولم يُضف proof artifact منفصل: في غياب Composer وLaravel scaffold، لن يثبت PHP mock مستقل تسجيل Laravel providers أو توافق packages أو database locking أو transactional outbox، وقد يوحي بأدلة غير موجودة. أصغر prototype ذي معنى هو vertical slice مؤقت بين moduleين مالكين، مثلاً Sales → Inventory reservation، مع port/adapter binding عبر module provider ومسار transactional outbox/inbox واختبارات سلبية لـscope/SoD وduplicate delivery وrollback والتزامن.

يمكن لـlocal spike محدود، إذا وافق عليه المالك المختص صراحة ضمن نطاق منفصل، أن ينتج أدلة تقنية دون أن يعني production approval. لا يمنح هذا ADR إذناً بتنفيذ spike أو إنشاء scaffold. وبعد اعتماد scaffold واختيار قاعدة البيانات، تكون runtime/database proofs المطلوبة للتشغيل الفعلي مرحلة تحقق لاحقة؛ ولا تُشترط هذه الأدلة اللاحقة لقبول الخيار المعماري نفسه. ولا يضاف Finance posting contract إلى spike إلا بعد توقيع السياسة المناسبة؛ ويجب ألا يخترع spike سياسات OPEN-03/04/05. تُسجل الأوامر والإصدارات الدقيقة ومحرك القاعدة ومخرجات الاختبارات والمراجعين كأدلة؛ ولا تعد هذه الوثيقة موافقة إنتاج.

## قيود runtime وأدلة الدعم الرسمية

**وقت فحص البيئة المحلية (`Get-Date -Format o`):** `2026-10-15T19:34:11.7999207+03:00`.

**وقت جلب صفحات الدعم الرسمية:** غير موثق بدقة في سجل هذه المهمة؛ يجب إعادة التحقق من دورة الدعم عند اعتماد stack وقبل production.

تم فحص توفر الأدوات للقراءة فقط باستخدام `Get-Command php,composer,node,npm,docker,pwsh`، كما نُفذت أوامر `php -v` وقراءة إصدارات Node/npm. أظهر الفحص التفصيلي الأدوات الغائبة صراحة؛ أما الاستعلام المجمع فأظهر الأدوات الموجودة وانتهى بـ`[exit code: 1]` مع أسماء الغائبين غير ظاهرة بسبب `SilentlyContinue`.

| الأداة | الرصد المحلي | القيد والتفسير |
|---|---|---|
| PHP | موجود، PHP 8.4.21 CLI | executable محلي، وليس اختيار runtime للمشروع أو دليلاً على deployment. |
| Composer | غير موجود | لا يمكن حل أو تثبيت Laravel/packages، أو إنشاء lockfile، أو تنفيذ Composer audit، أو إثبات توافق dependencies. لم يُثبت في هذه المهمة. |
| Node / npm | موجودان، v24.15.0 / 11.12.1 | متاحان محلياً، لكنهما لا يثبتان صلاحية PHP application/runtime. |
| Docker | غير موجود | لا يتوفر إثبات محلي لقاعدة بيانات/runtime داخل container. لم يُثبت في هذه المهمة. |
| `pwsh` | غير موجود؛ executor هو Windows PowerShell 5.1 | يمكن استدعاء فحص الوثائق في جلسة PowerShell الحالية؛ غياب `pwsh` دليل بيئة وليس طلباً لتثبيته. |

كانت صفحات الدعم والإصدارات الرسمية متاحة ضمن التقييم؛ وهي دليل دورة دعم فقط، لا build أو compatibility test:

- تذكر [Laravel 13.x release notes](https://laravel.com/framework/docs/13.x/releases) دعم PHP 8.3–8.5، وإصدار Laravel 13 في March 17, 2026، وإصلاحات bugs حتى Q3 2027 وإصلاحات security حتى March 17, 2028. وتذكر [Laravel 12.x release notes](https://laravel.com/framework/docs/12.x/releases) إصلاحات security حتى February 24, 2027. هذه التواريخ المنشورة تجعل 13.x مرشحاً للتقييم مقارنة بـ12.x لبناء جديد؛ ولا تتضمن ادعاءً غير موثق بأنه universally “latest”.
- تذكر صفحة PHP الرسمية [Supported Versions](https://www.php.net/supported-versions.php) استمرار دعم security لـPHP 8.4 حتى December 31, 2028 وPHP 8.5 حتى December 31, 2029، ولـPHP 8.3 حتى December 31, 2027.
- استُخدمت [Laravel 13.x service-provider documentation](https://laravel.com/framework/docs/13.x/providers) لتقييم composition-root seam المقترح أعلاه.

**مرشح runtime مقترح للتحقق:** Laravel 13.x مع PHP 8.4.x؛ إذ يشمل نطاق Laravel المنشور فرع PHP 8.4 الموجود محلياً، وتاريخ دعمه المنشور أطول من Laravel 12 وقت إعداد هذا التقييم. يظل ذلك Proposed، وليس stack معتمداً أو patch pin أو Composer constraint أو توصية deployment. يجب إعادة فحص دورة الدعم والتوافق وقت اعتماد stack وقبل production. PHP 8.5 مدرج أيضاً ضمن دعم Laravel 13 لكنه غير موجود محلياً. تبقى قاعدة البيانات والـqueue والـcache والـsearch والـstorage والاستضافة والحزم الفردية غير محسومة. لم يتسنّ تنفيذ Composer/package resolution أو اختبار دعم في production.

## قائمة المراجعة: الاعتمادات والأدلة الناقصة

الأدوار أدناه من ADR/PRD/سجل القرارات المفتوحة؛ لا تُفترض أسماء أفراد أو تواريخ أو موافقات.

### معنى قبول هذا ADR

قبول هذا ADR يعني اعتماد الخيار المعماري فقط بعد تسجيل قرار Engineering + Product وتاريخه ومبرراته. لا يعتمد ذلك Laravel/PHP versions أو packages أو قاعدة البيانات أو queue أو hosting، ولا يغلق أي `OPEN-*`. كما لا يتطلب تشغيل runtime/database tests التي لا تصبح ممكنة إلا بعد scaffold واختيار المحرك؛ تلك أدلة لاحقة لازمة للبوابات التنفيذية/الإنتاجية المعنية. يمكن لإذن منفصل من المالك إجراء local spike لإنتاج دليل دون production approval، لكنه لا يعني اعتماد stack أو business policy ولا يجيز scaffold. لا يوجد حتى الآن sign-off أو تاريخ؛ لذلك يظل ADR-001 بحالة Proposed.

## بوابة scaffold والحالة الحالية

يسجل task record أن `A0-ADR-001` جاهز للتقييم، وأن `A0-ARCH-901` (Laravel skeleton) محجوب بـ`A0-ARCH-900` و`A0-ADR-001` و`A0-ADR-002` و`A0-ADR-008`. يقدم هذا ADR توصية وسجل أدلة فقط، ولا يرفع أي حجب أو يغير task status. يظل ADR-002 وADR-008 مفتوحين، ولا يستبدل هذا التقييم مهمة تصميم finance/stock. حتى قبول الخيار المعماري لا يمنح وحده إذناً بإنشاء scaffold.

## سجل القرار

**القرار:** غير معتمد. Status remains Proposed.

**مالك/مالكو الاعتماد:** Engineering + Product؛ والمالكون الإضافيون أعلاه لقراراتهم وأدلتهم.

**تاريخ الاعتماد:** غير مسجل.

**دليل القبول:** لا يوجد sign-off من المالكين، أو Laravel install/package resolution، أو application prototype، أو proof لمعاملات/concurrency قاعدة البيانات، أو اعتماد لسياسات الأعمال، أو دليل runtime للإنتاج. يسجل هذا المستند توصية معمارية مشروطة ونطاق الأدلة المحلية والرسمية فقط.
