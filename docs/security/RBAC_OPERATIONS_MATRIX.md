# My Arasya — Requirements-driven RBAC and operations matrix

Analysis date: 2026-10-18. Project: `C:\projects\new_arasya-crm`.

**Status: implementation reference for owner review, NOT an approved permission policy.**

This report inventories required operations and compares them with the current working-tree implementation. It does not authorize new roles, grants, approval chains, thresholds, integrations or implementation. Unknown policy is deliberately recorded as **OWNER DECISION REQUIRED**, not filled with an assumed permission.

The original analysis was read-only. The owner's subsequent instruction authorized saving this Markdown report only. No application code, database, task state, permission seed, ADR, OPEN decision or Git commit was changed for this report.

## Reading the matrix

This is a normalized matrix: A defines business actors; B and C define operations; D defines actual permission precedence and scope; E defines navigation; F defines denial tests; G defines policy decisions; H records gaps; I distinguishes existing keys from proposals; J supplies the owner checklist. Read those sections together rather than treating an actor label or a permission alone as sufficient authorization.

Where several atomic actions occupy one cell, they are independent operations with the same stated constraints, not one combined endpoint or permission grant. Action labels are normalized analysis decompositions of the cited requirements/workflows, not necessarily verbatim PRD verbs or approved command names. Logical future page/resource names describe requirements; they do not imply approved screen prototypes or working URLs. Conditional capabilities remain conditional, especially optional signatures/channels and any future policy-authorized disposal.

### Evidence and classification

| Marker | Meaning |
|---|---|
| E — Explicit | An operation/control is stated in requirements, or behavior is directly observed in source. Explicit code behavior is not automatically approved business policy. |
| I — Inferred | Actor-to-operation association or logical screen grouping inferred from documented responsibilities/proposed design; not an approved default grant. |
| U — Undetermined | Authority, scope, state contract or policy is unspecified/unresolved. **OWNER DECISION REQUIRED** before activation. |
| IT — IMPLEMENTED & TESTED | Reserved for an identified implementation with applicable executed evidence. No current-tree runtime verification was performed in this analysis. Historical evidence is listed separately below. |
| IU — IMPLEMENTED BUT UNVERIFIED | Current source has the bounded operation, often with test source, but it was not freshly executed for this report. |
| P — PARTIAL | Some primitives, fields, routes or controls exist, but the full requirement/workflow does not. |
| M — MISSING | A required operation/enforcement is absent in an otherwise implemented area. |
| B — BLOCKED BY OWNER DECISION | A relevant OPEN/ADR policy prevents final authorization/activation; implementation may also be absent. |
| N — NOT YET IN IMPLEMENTATION PHASE | Approved later-increment resource has no business runtime implementation; this does not remove applicable policy gates. |

An IU row must not be promoted to IT because a related task is DONE. Historical test runs do not prove all changes in the current dirty tree.

### Common controls and audit notation

- Every business permission remains subject to current authentication, record and field scope, workflow validation and applicable approval. Hidden/disabled controls are never sufficient enforcement.
- `A` means the SEC-05 required audit: actor, effective role, action, entity/record, secure before/after diff, approval path, timestamp, correlation ID, origin and outcome. Sensitive denied attempts also require appropriate security evidence (AT-01/AT-14). Current implementations do not establish complete tamper protection or comprehensive denied-attempt coverage.
- `H` means immutable/versioned workflow or revision history, in addition to `A` where consequential. `D` means document access/version/checksum evidence. `X` means access/export/download audit. These are required controls, not invented event names.
- Ordinary read audit is not assumed mandatory everywhere; `—` means no separate read approval/audit specified, not an exemption from privacy/access controls.
- `v` means current expected record version. `W` means detailed state names/edges come from the **Proposed** workflow catalog rather than an activated policy. PRD lifecycle names are mandatory where explicitly stated.
- Contacts remain masked unless an explicit authorized, audited disclosure applies. Employment-private data, compensation and finance processing rights are separate; director/administrator labels do not make them public.

- `EmployeeProfile.role` is employment information, not a technical grant. `access_users.is_admin` is a separate technical elevation flag, not the Director or SA actor description.

The demo can grant `contact.reveal` explicitly through a role; that is different from the root flag's defaults.
- Schema, grant resolution, fixtures and seed source were inspected. No running database was queried, so this report does **not** enumerate real users, currently stored role names or actual individual exceptions. A later owner-authorized entitlement inventory must read those rows without confusing them with normative policy.
