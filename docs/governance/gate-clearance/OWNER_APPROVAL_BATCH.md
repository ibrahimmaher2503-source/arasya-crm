# دفعة تأكيدات المالك — My Arasya

> **ورقة عرض قصيرة وليست موافقة أو تفويضاً.** baseline `4b55a00`؛ لا قبول ADR أو اعتماد OPEN أو تغيير نطاق أو حالة مهمة بهذا التقرير. لم يُستنتج قبول من الطلب الحالي أو كلمة «متابعة». لم تُعد توليد أي وثيقة أخرى.

## ما يمكن عرضه الآن

**مرشح وحيد: ADR-001، قرار تصميمي محدود**: قبول structured Laravel modular monolith بتطبيق قابل للنشر واحد وحدود ownership صريحة، وعقود Application scoped، ومالك كتابة واحد لكل aggregate، بلا shared mutable models أو اعتماد دائري. يبقى stack/runtime/package/DB/queue/cache/hosting والسياسات والإنشاء والتنفيذ خارج القرار. مقارنة البدائل والمبررات والحدود موجودة في [ADR-001](../../architecture/adr/ADR-001.md#L18-L33) و[كتالوج الوحدات](../../architecture/MODULE_CATALOG.md#L1-L27)، وتوصي PRD بالبنية المعيارية؛ لا يلزم إثبات DB/runtime لقبول المعمارية وحدها.

سجل [الموافقة الجزئية](../decision-approvals/ADR-001.md#L3-L43) يقول إن Ibrahim، بصفته Product Owner، سجّل Product Approved بتاريخ `2026-10-16`؛ القرار الإجمالي لا يزال Pending وEngineering Pending. Ibrahim مخوّل هنا بدوري Product وEngineering؛ لا تفرض المصادر التي راجعتها شخصين مختلفين، فيجوز له توثيق قرار صريح منفصل لكل دور. يلزم مع ذلك نص Engineering acceptance مستقل ومحدد، ولا يحوّل ذلك مراجعة تقنية إلى اعتماد: مراجعة `A0-ARCH-001` المستقلة في [handoff](../loop/handoffs/A0-ARCH-001-f5890f4be36f4c249bb78c0e2b0b5c4b.md#L18-L19) قبلت read-model ضيقاً بعد إصلاحين، وليست قبولاً لـADR-001. لا يوجد في هذا الطلب قبول صريح للـADR.

- النتيجة الافتراضية لو قُبل ADR-001 وحده: `A0-CORE-900` (مباشرة واحدة، حالتها المحفوظة `blocked`) تصبح مؤهلة اعتمادياً فقط؛ شرط المهمة `A0-ARCH-901` منجز، وADR-001 بوابتها الوحيدة. لا تُصبح `ready` إلا بعد سجل رسمي صحيح ثم إعادة تقييم منفصلة من coordinator مخول، ومع إذن تنفيذ مستقل.
- دفعة مشتركة لاحقة ADR-002 + ADR-003: `A0-ARCH-902` وحدها تصبح مؤهلة اعتمادياً؛ شرط المهمة مسجل مكتمل، لكن كل قرار مطلوب، وحالتها `blocked`. قبول ADR-002 وحده أو ADR-003 وحده لا يفتحها. لا اختبار/تثبيت/اتصال DB مطلوب لمجرد تصميم القرار.
- OPEN-10 وحده: `A0-DOC-001` تصبح مؤهلة اعتمادياً؛ لا prerequisites مسجلة، لكنها محفوظة `blocked` وتحتاج إعادة تقييم coordinator. لا يعني ذلك قبول retention policy أو تفعيل حذف/وصول.
- `Status` و`Ready` اللذان شُغّلا أدناه أظهرا حالياً `currently_ready=0`؛ لا يوجد task جاهز للتنفيذ الآن. لا ينشئ أي عدّ counterfactual إذناً أو يغير الحجب.

## تحقق تقني لاحق مقترح فقط — ADR-002/003

تعيد الخطة استخدام الحالات الثماني المسماة في [خارطة الطريق](GATE_CLEARANCE_ROADMAP.md#L7-L10): `ADR002-RACE-RESERVE`، `ADR002-RACE-ISSUE`، `ADR002-RACE-PERIOD-CLOSE`، `ADR002-MONEY-DECIMAL`، `ADR002-UNIQUE-SCOPE-FK`، `ADR002-IDENTIFIER-COMPAT`، `ADR002-MIGRATION-FORWARD`، `ADR002-BACKUP-RESTORE`. المعرّفات أعلاه هي cases قبول مقترحة **غير منفذة**. يحدد Engineering + Finance (ومعهم IT/Operations حيث يلزم) target MariaDB version، PDO driver، transactional engine، isolation/locking، disposable DB/data location معزول، signed decimal/rounding/overflow fixtures، owner expected restore/RPO/RTO وpass criteria؛ Engineering/IT يحددان قيود التزامن للـqueue/search. لا تستنتج compatibility من Laravel config أو SQLite. لا تثبيت DB، لا اتصال أو test execution، لا production/real credentials، ولا cleanup/deletion هنا. حالات ADR-003 تتطلب خطة منفصلة للإرسال/النشر race، duplicate/replay، crash/retry/DLQ، worker outage، reauthorization/masking/search scope، وصفر آثار خارجية؛ لا نعدها ضمن الثماني ولا نعلن اختباراً منفذاً.

## مدخلات المالك التالية والأعمال المشروطة

1. إن اختار المالك القبول، يرسل **قبولاً صريحاً** لـ`ADR-001` فقط ضمن حد التصميم أعلاه، مع Engineering وProduct role statements منفصلة (يجوز Ibrahim لكليهما)، السبب/البدائل والتاريخ. لا حاجة لاعتماد مراجعة التقنية كموافقة Engineering.
2. لا يتضمن batch الحالي موافقات ADR-002/003 أو OPEN. يلزم من المالكين المدخلات/الأدلة المبينة في صفوفها؛ ولا تُرقّى توصيات ULID أو moving weighted average أو أي costing/rates/rounding/defaults إلى اعتماد.
3. أول packets تنفيذ مشروطة بعد القبول الرسمي وسجل verifier ثم coordinator reassessment **وإذن coding/lifecycle منفصل**: `A0-CORE-900` (يتطلب `A0-ARCH-901` done وADR-001)، ثم حسب DAG فقط `A0-SEC-002` بعد `A0-SEC-001` و`A0-CORE-900`؛ لا نأذن ببدئها هنا. لمسار joint ADR-002+003: `A0-ARCH-902` بعد `A0-ARCH-901` وقراري ADR كليهما. لمسار OPEN-10: `A0-DOC-001` بلا task predecessor في الرسم، لكنه محفوظ blocked. ولا يفتح هذا التقرير عملاً حالياً.
4. الطلبات الخمسة في [مسودات change control](../proposals/PHASE-A-SCOPE-CHANGES.md) (email, SMS, WhatsApp, Telegram, practical AI) كلها غير معتمدة. أي deferral/fake-only يمس PRD MUST يلزمه قرار Product/المالك حسب change control قبل إعادة تصنيف أو task split/DAG؛ لا يلزم change لمجرد دعم synthetic لا يتنازل عن MUST. الأعمال المالية الفعلية تبقى محجوبة.

## لقطة الحالة وإعادة الحساب

قراءة `tasks.json` انتقت فقط `id`, `status`, `depends_on`, `decision_dependencies` (لم تُحلل نصوص tasks): SHA-256 `9B8D44AAFD792A3BA3761D7FBCDF129AE29A480283AA7A41CD626E24B403FD74`، 239 مهمة، `done=25`, `blocked=86`, `planned=128`. كل صفوف D أعلاه تشير إلى مهام مباشرة حالتها blocked. قراءات task-loop: `Status` و`Ready` كلاهما `active_leases=0`, `currently_ready=0`, `pending_transaction=none`. الحالة عرضة للتغيير المتزامن؛ أعد القراءة قبل أي قرار أو عمل. بعد إزالة التكرار: اتحاد المهام المباشرة = 86؛ واتحاد مجموعات descendant-only لكل قرار (مع استبعاد جميع direct roots الخاصة به) = 211؛ يتقاطع الاتحادان في 83 ID، واتحادهما الكلي = 214. هذه أعداد مجموعات لا وعود فتح.

إعادة اشتقاق read-only في Windows PowerShell 5.1: لكل قرار يبدأ البحث العكسي من direct roots، ثم يستبعد **كل** direct ID لهذا القرار وكل `done` من descendants؛ يحسب `immediate` بعد افتراض قبول ذلك القرار وحده (الأثر المشترك ADR-002+003 مذكور منفصلاً أعلاه).
