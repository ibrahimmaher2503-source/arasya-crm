# ADR-008 — بيئة التشغيل والاستضافة والعمليات

Status: OPEN

Owner: IT + Engineering

Decision date: غير مسجل

تاريخ رصد البيئة المحلية: `2026-10-15T19:53:39.5782153+03:00`

## خلاصة التقييم وحدود القرار

اختار المستخدم Laravel، وأكد تفضيل `package-first` كمنهج تقييم؛ لا يعني ذلك اعتماد إصدار Laravel أو PHP، أو package، أو مزود خدمة، أو نموذج استضافة. تبقى هذه الخيارات، وكذلك قاعدة البيانات وqueue وcache والتخزين وSLO/RPO/RTO، `Proposed` أو `OPEN` إلى أن يقدم مالك القرار خياراً موقعاً ودليله.

يفصل هذا التقييم بين قرارين مستقلين:

1. **اعتماد أدوات التطوير المحلية:** قرار محدود لـEngineering وIT بشأن PHP/Composer وإصدار Laravel الذي يمكن استخدامه محلياً، وحدود scaffold أو spike محلي. لا يتطلب اختيار مستضيف إنتاج، ولا تحديد أرقام SLO/RPO/RTO، ولا إثبات نشر production كامل. نجاح الاختبار المحلي دليل تطوير فقط.
2. **اعتماد استضافة production والتشغيل:** قرار IT وEngineering وفق `OPEN-11`، ويحتاج profile للأحمال والبيانات، أهدافاً رقمية معتمدة، مراجعة الأمن والتكلفة التعاقدية، وخطة backup/restore ودليل اختبار فعلي. لا يمنح اعتماد الأدوات المحلية موافقة نشر أو موافقة على مزود أو سعة إنتاج.

توصية هذا التقييم هي السماح **ببوابة محلية منفصلة** بعد موافقة صريحة على أدوات التطوير وخط إصدار مدعوم، بدلاً من اشتراط proof لنظام production منشور قبل إنشاء scaffold محلي. لا يغير هذا المستند `tasks.json`: المهمة `A0-ARCH-901` تسجل حالياً `A0-ADR-008` ضمن `depends_on`. لذلك يبقى الحجب كما هو في سجل المهام إلى أن يوثق المالك قراره ويحدّث coordinator بوابة المهمة صراحةً؛ وعندها ينبغي أن تكون موافقة `A0-ADR-008` المطلوبة للـscaffold محلية ومحددة، مع بقاء بوابة production منفصلة قبل أي نشر. لا ينبغي تفسير الاقتراح هنا على أنه رفع للحجب أو تنفيذ scaffold.

لا يختار التقييم بين managed وself-hosted: لا توجد أدلة `OPEN-11` عن المستخدمين أو الأحمال أو الكلفة أو مهارات التشغيل أو أهداف التعافي تبرر اختياراً. التطبيق يظل My Arasya الداخلي لشركة واحدة؛ استخدام خدمة بنية تحتية managed لا يحول المنتج إلى SaaS، ويشترط بقاء الوصول والعزل والحوكمة تحت سيطرة Arasya.

## القيود المؤكدة ومصادر المتطلبات

- يطلب PRD نشرًا خاصاً لشركة واحدة، وauthorization على الخادم، وprivate storage للوثائق، وrelational transactional database، وbackground jobs، وsecret management، ونسخاً احتياطية مشفرة واختبار استعادة (`NFR-01` و`NFR-03` و`NFR-04` و`NFR-07` و`DOC-01/02` و`ARCH-01/02/03`).
- يقترح [تصميم الحل](../SOLUTION_ARCHITECTURE.md) تطبيقاً واحداً قابلاً للنشر مع workers منفصلة تشغيلياً، قاعدة علائقية، outbox موثوقاً، وتخزيناً خاصاً؛ محركات الخدمات والاستضافة تبقى `OPEN`.
- يطلب [دليل التشغيل](../../operations/DEVOPS_RUNBOOK.md) بيئات وبيانات وأسرار منفصلة، وworker drain عند النشر، ومراقبة queue، ونسخاً تشمل DB والوثائق ومفاتيح الاستعادة المحمية، وتجربة restore تقيس النتيجة الفعلية.
- يسجل [سجل القرارات المفتوحة](../../governance/OPEN_DECISIONS.md) `OPEN-11` بمالكَي `IT + Engineering`، وبحاجز قبل production infrastructure، ويطلب user counts/load profile وnumeric SLO/RPO/RTO وخطة migration وrestore drill. لا توجد في السجل أرقام أو موافقة إنتاج.
- تحدد [استراتيجية الاختبار](../../engineering/TEST_STRATEGY.md) أن performance thresholds وvolumes تنتظر `OPEN-11`، وأن database race tests يجب أن تعمل على المحرك الذي سيُعتمد لا على بديل يخفي locking.
- نطاق المهمة `A0-ADR-008` في [سجل المهام](../../backlog/tasks.json) هو هذا الملف وحده، ومطلوبها مقارنة موثقة مع اعتماد المالك أو الأسئلة غير المحسومة؛ ولا تخول تغيير task state أو سجلات أخرى.

### اقتراح bootstrap محلي أدنى — غير منفذ

1. يقرر `Engineering + IT` منفصلاً إن كان مسموحاً استخدام PHP المحلي الحالي مؤقتاً للتطوير، ويختاران إصدار Laravel/PHP محدداً بعد التحقق من دورة الدعم والمتطلبات في حينها. لا يُستنتج من وجود PHP محلي اختيار إصدار للمشروع.
2. إذا وافق المالكان على Composer محلياً، فالمرشح الأقل تدخلاً هو `composer.phar` داخل مسار محلي مؤقت مثل `.tools/composer.phar`، دون تثبيت global أو تعديل `PATH`. قبل استعماله، ينزّل المسؤول ملف Composer من [صفحة Composer الرسمية](https://getcomposer.org/download/)، ويتحقق من SHA-384 للـinstaller بالقيمة المنشورة الحالية في الصفحة، أو من SHA-256/PGP للـPHAR وفق ما تنشره الصفحة، ثم يسجل الإصدار والبصمة ومصدر التنزيل. ينبغي التأكد من أن المسار المحلي غير مضاف إلى ملفات المصدر؛ لم يُنشأ هذا المسار أو تُنزّل أي ملفات هنا.
3. بعد موافقة أدوات التطوير وإصدار framework، يمكن للمالك تفويض scaffold معزول للحد الأدنى من `laravel/laravel`، دون مزود خارجي أو أسرار أو packages إضافية أو business migrations. صيغة مقترحة للتنفيذ المستقبلي فقط:

   ```text
   php .tools/composer.phar create-project laravel/laravel <scratch-path> <approved-version-constraint>
   ```

4. يتحقق ذلك النطاق محلياً من `php -v` والامتدادات، و`composer validate` و`composer check-platform-reqs`، ثم من تشغيل Laravel baseline و`php artisan test` على scaffold المعزول. هذه checks لا تختار production database ولا تثبت database locking أو capacity أو recovery. لا يعد استخدام قاعدة اختبار محلية بديلاً عن engine-specific integration tests بعد اعتماد المحرك.
5. لم تنفذ أي خطوة من هذه الخطوات في هذا التقييم. ولا توجد موافقة حالية على PHAR أو scaffold؛ إنما هي أصغر آلية قابلة للقرار لفك اعتماد أدوات التطوير عن استضافة الإنتاج. يظل `package-first` معياراً لتقييم قدرات Laravel/first-party أو package مناسبة لاحقاً؛ لا توجد package إضافية موصى بها أو معتمدة هنا.

## مقارنة بدائل الاستضافة والتشغيل

تُطبق الشروط نفسها على البديلين: نسخة تطبيق واحدة قابلة للتكرار، HTTP runtime منفصل تشغيلياً عن queue workers من codebase نفسه، وrelational database مصدر الحقيقة، وprivate storage للملفات. تظل محركات queue وdatabase وstorage وخدمات الاستضافة بلا اختيار حتى قرار المالك.

| المجال | Managed | Self-hosted |
|---|---|---|
| تشغيل Laravel | قد تدير الخدمة طبقة PHP/web runtime والنشر أو بعض أعمال الصيانة؛ يجب التحقق تعاقدياً من إصدار PHP/extensions، وحدود الشبكة، والنشر والتراجع، ومكان البيانات. لا يُفترض دعم PHP أو صلاحية كل خدمة قبل إثباتها. | تدير Arasya أو مشغلها المضيف، PHP runtime، web server/reverse proxy، TLS، تحديثات النظام وPHP، صلاحيات الملفات، والنشر والتراجع. تمنح تحكماً أكبر، لكنها تنقل عبء التحديث والاستجابة التشغيلية إلى المشغل. |
| Queue وworkers | يجب إثبات وجود طريقة مدعومة لتشغيل queue workers طويلة العمر منفصلة عن HTTP، وإعادة تشغيلها بأمان بعد النشر، ومراقبة الفشل والتوسع/القيود. لا يُفترض أن المنصة أو الخطة تقدم worker service أو scheduler. | يشغّل المشغل workers كعمليات منفصلة تحت process supervision، ويحدد restart/drain وtimeouts وmemory limits والمراقبة والتنبيه وإجراء DLQ/replay. يتحمل إعداد السعة والتعافي وفشل المضيف. |
| Relational database | يمكن استخدام خدمة DB مُدارة إذا ثبت المحرك والإصدار المدعوم والاتصال الخاص والتشفير وسياسة backup ووقت/طريقة restore والفشل/الترقية وإمكانية استخراج البيانات. يجب التحقق من حدود الاتصالات والتزامن والمحرك الفعلي. | يختار المشغل وينفذ محرك relational database والشبكة الخاصة والتحديثات وHA/replication والضبط ومراقبة الاتصالات والنسخ والاستعادة والتصحيح الأمني. لا يوجد دليل حالياً يبرر اختيار محرك بعينه. |
| التخزين الخاص | لا تقبل الخدمة إلا إذا أمكن إبقاء الملفات private افتراضياً، وتطبيق صلاحيات دقيقة، وتشفيرها، والتحقق من download authorization، ودمج الملفات ونسخها واستعادتها مع DB. التحقق مطلوب من سلوك URLs المؤقتة ونسخ الكائنات وحذفها. | يضبط المشغل private filesystem أو object storage، ومفاتيح الوصول والتشفير، والحصة/المراقبة، وquarantine وفحص الملفات وchecksum، والنسخ والاستعادة، ومنع web root العام من خدمة الوثائق. |
| الأمن والأسرار | يلزم إثبات region/data handling والعزل وsupport access وسجل التدقيق وآلية secret manager وrotation وincident response بالعقد والتهيئة الفعلية. تبقى مسؤولية إعداد تطبيق Laravel، least privilege، إخفاء PII، وعدم كشف الأسرار مسؤولية مالكي النظام. | يتحمل المشغل إعداد network isolation وTLS وpatching والهوية وleast privilege وsecret manager أو آلية محمية معتمدة، وتدوير/revocation الأسرار وحماية المفاتيح والسجلات من التسريب. لا توضع secrets في source، artifacts، صور التشغيل أو logs. |
| Backup وrestore | لا تعتبر عبارة “managed backups” دليلاً كافياً: يلزم توثيق نطاق النسخ، retention، encryption/key recovery، التناسق بين DB وprivate files، وإثبات استعادة قابلة للتنفيذ مع قياس فعلي. تعتمد المساءلة على حدود العقد وما يبقى على Arasya. | يملك المشغل تصميم النسخ المشفرة/offsite والاحتفاظ وحماية المفاتيح والmanifest/checksums واختبار restore والعزل والتسوية بعد الاستعادة؛ ويجب أن يخصص الأشخاص والوقت والأدوات اللازمة لذلك. |
| المقايضة والملاءمة | قد تقلل تشغيل البنية الأساسية التي يديرها فريق Arasya، لكنها لا تثبت تلقائياً التوافق أو التعافي، وتحتاج بيانات موثقة عن القيود والتعاقد وdata residency والتصدير والاعتماد على المزود. لا توجد عروض أسعار أو تقييم vendor هنا. | تمنح تحكماً مباشراً أكثر في الشبكة والتهيئة، لكنها تتطلب ملكية فعلية للتحديثات والسعة والنسخ وon-call وincident response. لا توجد بيانات عن staffing أو كلفة أو قدرة داخلية تبررها حالياً. |

بغض النظر عن المستضيف، يكون `database` متاحاً فقط عبر شبكة خاصة وبصلاحيات مستقلة للتطبيق والworkers؛ لا اتصال عام غير مقيد. تكون uploads والوثائق غير عامة ويُتحقق من التفويض قبل العرض، مع quarantine/scan/checksum وفق التصميم. تدار الأسرار خارج ملفات source وdeployment artifacts، وتحدد صلاحيات وrotation/revocation ومسؤولية الوصول. تُحفظ تغييرات domain وoutbox داخل transaction واحدة، وتكون إعادة التسليم `at-least-once` مع idempotent consumers ومراقبة retry/DLQ؛ لا يُدّعى `exactly-once` عبر الشبكة. تشرح [Laravel queues](https://laravel.com/framework/docs/13.x/queues) نمط workers وإدارة jobs، وتشرح [Laravel filesystem](https://laravel.com/framework/docs/13.x/filesystem) خيارات disks والتخزين؛ ولا تعين هذه الوثائق مزوداً أو سياسة تشغيل لـMy Arasya.

**الموازنة الموصى بها حالياً:** اعتماد متطلبات capability والأمن والتعافي أعلاه كمعايير مقارنة، وتأجيل اختيار managed مقابل self-hosted حتى يقدم مالكا `OPEN-11` ملف الأحمال واحتياجات الدعم والعروض/قيود الاستضافة. لا يُخترع سعر أو عدد مستخدمين أو حساب أو مزود أو credential في هذا ADR.

## قائمة جاهزية production قبل قبول الاستضافة

- [ ] يثبت `IT + Engineering` نموذج النشر والحدود بين HTTP runtime وworkers وscheduler، ويحدد من يدير كل خدمة وكيفية النشر الآمن وdrain/restart/rollback.
- [ ] يختار المالكان Laravel/PHP versions مدعومة وموثقة، ويراجعان framework/package lifecycle وComposer lock وsecurity advisories قبل artifact release.
- [ ] يوثق `OPEN-11` user counts وconcurrent load وAPI/job mix وبيانات البداية والنمو/imports وأوقات الذروة؛ جميع القيم تنتظر المالك ولا يفترضها هذا ADR.
- [ ] يقدم مالكا الاستضافة وثائق capabilities وقيود الشبكة وregion/data handling والدعم والتصدير والعقد وعرض الأسعار الفعلي قبل اختيار provider؛ لا توجد عروض أو موافقات حالياً.
- [ ] يعتمد المحرك العلائقي وإصداره وtransaction/locking/backups، ويختبر اتصالاته الخاصة وحساباته وصلاحياته؛ لا يفتح DB للإنترنت.
- [ ] يحدد queue backend والworker lifecycle والـscheduler وretry/backoff وDLQ وإعادة التشغيل والمراقبة؛ ويثبت سلامة outbox/inbox وعدم ازدواج الأثر عند failure/replay.
- [ ] يثبت أن التخزين private افتراضياً، ومفصول عن public web root، مع authorization قبل download، وupload validation/quarantine/scan وintegrity checks وسياسة احتفاظ معتمدة.
- [ ] يعتمد secrets management وkey custody، service identities منفصلة وأقل صلاحية، rotation/revocation، ومنع الأسرار وPII من source وimages/artifacts وlogs. تُراجع سياسات الاحتفاظ والمسوغ القانوني مع ملاك `OPEN-10` عند الحاجة.
- [ ] يبني artifact قابلاً للتكرار لا يحتوي `.env` أو مفاتيح، ويجرب migrations وcompatibility/rollback أو recovery strategy على بيئة مماثلة قبل release، ويعطل `APP_DEBUG` في production ويوجه web root إلى `public/`، مع health checks وrelease approval.
- [ ] تغطي النسخ المشفرة DB والملفات الخاصة وmanifest/checksums ومفاتيح استعادة محمية، وretention/offsite وفق القرار المعتمد. restore drill حقيقي يعيد DB والملفات إلى بيئة معزولة ويتحقق من سلامة journal/stock والpermissions قبل فتح traffic.
- [ ] يجهز مراقبة availability وrequest latency/errors وDB saturation وqueue depth/age/retry/DLQ/outbox lag وstorage failures وsecurity events، مع سجلات منقحة بلا بيانات حساسة ومالكي تنبيه/تصعيد معروفين.
- [ ] يعتمد runbooks ومسؤولية on-call وincident containment وprovider disable وbackup/restore والتمرين، ويثبت من يراجع دليل الاختبار ومن يصرح بإعادة فتح traffic.
- [ ] يربط أدلة السعة والأمن والتعافي بمتطلبات PRD و`OPEN-11`، ويوقع المالك القرار قبل أي production deployment؛ وجود feature عند المزود أو نجاح local smoke لا يغني عن هذه البوابة.

## اختبارات قابلة للقياس تنتظر قيم المالك

هذه اختبارات قبول مقترحة، وليست نتائج منفذة. لا يمكن تحديد pass thresholds رقمية قبل أن يعتمد المالكان قيم `OPEN-11` وفترات القياس والبيئة والـload profile.

| الاختبار | ما يسجل فعلياً | معيار القبول الذي لم يحدده المالك بعد |
|---|---|---|
| Availability وhealth | نسبة النجاح والأخطاء والانقطاعات ضمن فترة قياس متفق عليها، مع فصل الصيانة المخططة والحوادث بحسب السياسة. | قيمة SLO، نافذة القياس والاستثناءات ودرجة التوفر المستهدفة؛ كلها غير مقدمة. |
| Performance/capacity | request latency percentiles وthroughput وCPU/memory/DB saturation، مع dataset وconcurrency وjob mix موثقين. | أعداد المستخدمين المتزامنين وحجم/نمو البيانات وحدود latency/throughput؛ تنتظر load profile وSLO موقعين. |
| Queue resilience | oldest-job age وqueue depth وretry/DLQ وoutbox lag قبل/بعد إسقاط worker أو عزل dependency، وإثبات idempotency وعدم فقد/تكرار business effects. | حدود age/depth/lag ومهلة التعافي التشغيلية ومعدل المعالجة المطلوب؛ لم تحدد بعد. |
| Restore/RPO/RTO | وقت بدء ونهاية restore، آخر record قابل للاستعادة، hashes/files completeness، وصحة journal/stock/permissions بعد المصالحة. تسجل RPO/RTO المقاسة فعلياً وتقارنها بالهدف. | قيم RPO/RTO الموقعة ونطاق البيانات ونقطة القياس؛ لا توجد أرقام معتمدة ولا restore drill evidence. |
| Private network وauthorization | اختبار أن الاتصال العام إلى DB/objects مرفوض، وأن أقل صلاحية تسمح فقط للـweb/worker/service identities المعتمدة؛ يثبت unauthorized file access بالرفض والتسجيل. | pass/fail حسب security review؛ identities وnetwork topology لم تُعتمد بعد. |
| Secret/log hygiene | فحص artifact/config/logs بحثاً عن secrets وPII، وتجربة rotation/revocation وفشل credential دون تسريب أو fail-open. | مالك secret manager وسياسة rotation والاحتفاظ ومراجعة Security؛ القيم والإجراء لم يعتمدوا. |
| Deployment/rollback | سجل مدة النشر والتراجع، worker drain/restart، توافق schema بين النسخ، ونتائج health checks مع jobs قيد التنفيذ. | حدود downtime/maintenance والـrollback criteria حسب SLO؛ لم يحددها المالك. |

تُقاس النتائج ببيئة وartifact ووقت وأمر قابلين لإعادة الإنتاج، وتُحفظ مخرجات آمنة ومنقحة. لا يعد اختبار SQLite أو local smoke دليلاً على engine-specific locking أو production capacity. لا توجد نتائج تطبيق/اختبارات Laravel في هذا التقييم لغياب `Composer` وLaravel scaffold.

## بيانات وأسئلة مطلوبة من المالكين والمشغلين

| المالك/الدور | المطلوب قبل قرار production | أثر غيابه |
|---|---|---|
| `IT + Engineering` (`OPEN-11`) | عدد المستخدمين المتوقع حسب الأدوار والتزامن والاتجاه الزمني؛ endpoints/workflows الحرجة؛ request/job/upload/report mix والذروة؛ حجم البيانات الأولي ومعدل نموها وmigration scope؛ حدود الشبكة والمنطقة؛ maintenance window؛ SLO وRPO وRTO بأرقام وفترات قياس معتمدة؛ restore drill ومسؤولية on-call. | لا يمكن اختيار السعة أو تحديد pass/fail للأداء أو availability أو recovery. |
| `IT + Engineering` ومراجع Security عند اللزوم | متطلبات private network، identity/service accounts، access review، secret/key custody، rotation/revocation، incident escalation، data export/exit، وساعات الدعم والمسؤوليات بين Arasya والمزود. | لا يمكن إثبات security ownership أو supportability أو استعادة البيانات والمفاتيح. |
| `IT + Engineering` مع المشتريات/الجهة المختصة إن وجدت | وثائق capabilities وعقد/حدود مسؤولية وعروض أسعار فعلية لكل بديل managed أو self-hosted، مع التحقق من worker/scheduler/DB/private storage/backup/restore وقيود المنطقة. | لا توجد قاعدة مقارنة اقتصادية أو تعاقدية؛ لا يجوز اختراع cost أو provider. |
| الإدارة/مالك المنتج بالتنسيق مع IT | أثر التوقف لكل مسار عمل، أوقات الصيانة الممكنة، وترتيب أولويات الاستعادة إذا لم تستعد كل الوظائف معاً. | لا يمكن تفسير availability target أو ترتيب failover والاستعادة بما يخدم العمل. |
| ملاك `OPEN-10` (`Legal + HR/Finance`) وSecurity عند اللزوم | retention، الوصول القانوني والموظفي، residency/transfer القيود ذات الصلة، وسياسة الاحتفاظ بنسخ production والوثائق. | لا يمكن إكمال retention/data-handling approval اعتماداً على ADR-008 وحده. |
| Operations/المشغل المعين بعد تحديده | أسماء الأدوار المناوبة لا أسماء مفترضة، إتاحة تشغيل/استعادة الخدمات، التصعيد، runbook owners، وتوقيع نتائج تمرين الاستعادة. | لا يثبت أن design قابل للتشغيل والدعم بعد الإطلاق. |

تُطلب قرارات الأدوار فقط؛ لا توجد أسماء أفراد أو حسابات أو credentials مثبتة في هذا المستند.

## حقول sign-off والحالة الحالية

لا يصبح أي خيار معتمداً بالتقادم أو بوجود توصية في هذا ADR. يوثق المالك كل قرار كدليل منفصل يتضمن `Decision` و`Owner` و`Approved on` و`Approved option` و`Evidence` و`Affected tasks` و`Tests` و`Review`، مع تحديث `OPEN_DECISIONS.md` وسجل المهام بواسطة المسؤول المخول فقط.

| حقل الاعتماد | بوابة أدوات التطوير المحلية | بوابة استضافة production |
|---|---|---|
| النطاق | محلي فقط؛ لا نشر ولا بيانات/أسرار production. | خدمة الإنتاج والبيانات والتشغيل والتعافي. |
| القرار الحالي | لم يعتمد؛ يلزم قرار منفصل من `Engineering + IT`. | غير معتمد؛ ADR-008 و`OPEN-11` باقيان `OPEN`. |
| الإصدار/الخيار | PHP وLaravel version وComposer acquisition/checksum: لم تعتمد؛ PHP المحلي المرصود معلومة بيئية فقط. | Laravel/PHP/runtime/provider/database/queue/storage: لم تحدد أو تعتمد. |
| الأدلة المطلوبة | توافق دعم رسمي وقت الاختيار، توثيق PHAR والتحقق من بصمته، وحدود scaffold والاختبارات المحلية. | مقارنة managed/self-hosted، بيانات الأحمال، security/contract review، قيم SLO/RPO/RTO، capacity/load وrestore evidence الفعلي. |
| المالك/التاريخ | الأدوار: `Engineering + IT`؛ اسم المعتمد وتاريخ القرار غير مسجلين. | `IT + Engineering`؛ اسم المعتمد وتاريخ القرار غير مسجلين. |
| الاختبارات/أثر المهمة | baseline local checks لم تنفذ؛ `A0-ARCH-901` لا يتغير بهذا المستند. | لا production tests أو deployment أو restore drill منفذة؛ تبقى مهام الإنتاج محجوبة حتى اعتماد الأدلة وتحديث coordinator للسجل. |
| دليل sign-off | غير متوفر. | غير متوفر. |

**الخلاصة:** لا توجد موافقة production أو أرقام SLO/RPO/RTO أو مزود استضافة/قاعدة/queue/storage معتمد. يوصي التقييم فقط ببوابة محلية مستقلة بعد موافقة `Engineering + IT`، مع عدم اشتراط نشر production لإثبات إمكان إنشاء scaffold محلي. يلزم أن يوثق المالك قراره وتاريخه ودليله، ثم يحدث coordinator أثره على `A0-ARCH-901`؛ إلى ذلك الحين يبقى `Status: OPEN` وتبقى حالة سجل المهام كما هي.
