# OPEN-11 — موجز أدلة البنية التحتية والسعة والتعافي

| الحقل | القيمة |
|---|---|
| المهمة | `A0-OPEN-11` |
| المالك وصاحب القرار | `IT + Engineering` |
| الحالة | `OPEN` — جمع أدلة وخيارات؛ لا اعتماد استضافة أو أهداف أو أسعار |
| نقطة الحجب | قبل بنية الإنتاج أو نشره؛ لا يحسم هذا الموجز أي قرار قانوني/تعاقدي |
| الغرض | ملف حمل قابل للتعبئة، ومقارنة قدرات، وخطة استيراد/نسخ/استعادة واختبارات قبول |

> املأ الحقول من مالكي البيانات والمشغلين. `TBC` أو الخانة الفارغة تعني «غير معلوم»، لا صفرًا أو قبولًا. لا تُدرج حسابات أو أسرارًا أو بيانات شخصية غير لازمة. تبقى `OPEN-11` مفتوحة إلى قرار المالك ودليله.

## 1. الحدود والثوابت

- المنتج نشر خاص لشركة واحدة. استخدام خدمة بنية تحتية مُدارة لا يحول المنتج إلى SaaS؛ يجب إثبات التحكم في الوصول والعزل والبيانات وفق ADR-008.
- أي خيار يجب أن يدعم authorization على الخادم، قاعدة علائقية transactional، وظائف خلفية، تخزينًا خاصًا للوثائق، إدارة أسرار، ونسخًا مشفرة واستعادة مختبرة. لا يُفترض أن خطة أو مزودًا يحقق هذه القدرات قبل توثيقها.
- بوابة تطوير محلي منفصلة عن بوابة الإنتاج: يمكن تقييم/إنشاء scaffold محلي بعد اعتماد أدواته ونطاقه محليًا؛ لا يلزم انتظار أرقام SLO/RPO/RTO أو اختيار استضافة الإنتاج. نجاح التطوير المحلي لا يجيز نشر الإنتاج ولا يرفع أي حجب مسجل.
- لا مزود أو محرك أو سعة أو قيمة رقمية أو توقيع معتمد في هذا الموجز.

| قاعدة البيانات | المحرك/الإصدار، معاملات/locking، اتصالات وقيودها، patch/upgrade، نسخ وPITR/restore، وتصدير قابل للاختبار. | من يدير المحرك والشبكة والتهيئة/الترقية والنسخ ومراقبة الاتصالات والاستعادة؟ هل بيئة الاختبار مطابقة؟ |

| الشبكة والأسرار | region/data handling، private connectivity، مفاتيح/KMS واستعادتها، support access، audit، rotation/revocation والتصدير بالعقد والتهيئة. | من يشغل العزل الشبكي، least privilege، secret/key custody، patching، rotation/revocation والاستجابة للحوادث؟ |
| التشغيل والخروج | ساعات الدعم والاستجابة المشمولة، الصيانة، حدود المسؤولية، قابلية تصدير DB/files، تكلفة/زمن الخروج والاعتماد على المزود. | عدد الأدوار/المهارات والتغطية اللازمة للترقيع والسعة والحوادث والنسخ والاستعادة؛ خطة بديل عند غياب المشغل. |

**أسئلة staffing والتكلفة:** من يملك كل خدمة، on-call والاستعادة والتحديثات خارج ساعات العمل؟ ما المهارات والتغطية البديلة والوقت التشغيلي المطلوب لكل بديل؟ اطلب عرضًا فعليًا مفصلًا بعملة وفترة صلاحية ونطاق واضح، يشمل compute/DB/workers/storage/egress/backup/logs/support/region والضرائب والزيادة والخروج؛ من جهة الشراء/الميزانية التي تُعيّنها Arasya. لا توجد أرقام تكلفة أو عروض أو حسابات/مزودون مثبتون هنا.

## 5. النسخ الاحتياطي ودليل تمرين الاستعادة

**النطاق المطلوب تقييمه:** قاعدة البيانات transactionally consistent وسجلاتها اللازمة للاستعادة؛ كل private documents ومراجعها/نسخها؛ manifest ومعرفات المصدر والإصدارات وhashes؛ ومواد/آلية استعادة مفاتيح التشفير والأسرار الضرورية. تبقى مفاتيح الاستعادة محمية ومنفصلة عن النسخة المشفرة، ويُختبر الوصول المصرح إليها دون كشفها. يحدد المالك آلية offsite/العزل، التشفير أثناء النقل والتخزين، فصل الصلاحيات، retention والحذف بالتنسيق مع `OPEN-10`، ودورية ومسؤولية الاختبار؛ لا تُفترض خدمة أو مدة.

ينفذ المشغل تمرينًا في شبكة معزولة، دون فتح traffic أو إرسال إلى providers: استعادة قاعدة البيانات والوثائق ومفاتيحها؛ تشغيل فحوص التكامل والتفويض؛ توثيق الانحرافات والوقت الفعلي؛ مقارنة RPO/RTO المقاسين فقط بالأهداف الموقعة. نجاح إنشاء backup وحده ليس دليل استعادة.

| دليل التمرين الواجب حفظه | ما يقاس/يسجل فعليًا |
|---|---|
| المصدر والنقطة الزمنية | معرف النسخة، المحرك/الإصدار، أوقات بدء/اكتمال DB والملفات، آخر حدث/معاملة مشمولة، المنطقة/بيئة الاستعادة |
| اكتمال البيانات | counts حسب الجداول/الفئات والملفات، manifest، منهجية النطاق، expected/actual والفروقات وتفسيرها |
| سلامة الملفات | hash المصدر/المستعاد أو تغطية العينة المعتمدة، عدد المراجع المفقودة/غير المتطابقة، واختبار فك التشفير بمفتاح مستعاد دون نشره |
| السلامة المالية والمخزنية | سجلات journal: مصدر/عدد/توازن ومصالحة؛ stock ledger/on-hand: counts ومصالحة بالحركات؛ anomalies وروابطها، دون تعديل المصدر لإخفائها |
| الهوية والتفويض | نجاح قراءة بهوية مخولة ورفض هوية/طلب غير مخول للوثائق والبيانات؛ تحقق session/service roles وسجلات audit المنقحة |
| نتيجة التعافي | وقت البداية والنهاية والمدة، نقطة البيانات المستعادة/الفقد الفعلي، RPO/RTO الفعلي، فرقها عن الهدف الموقع، الأعطال والإجراءات وإعادة الاختبار |
| الاعتماد | مشغل التمرين ومراجع IT/Engineering وتاريخ المراجعة، قرار إبقاء traffic مغلقًا أو فتحه، رابط الأدلة المنقحة؛ التوقيع غير متوفر حتى ينفذ التمرين |

## 6. خطة migration/import قابلة للتنفيذ

1. جرد المصادر والمالكين والنسخ/التواريخ والمخططات والنطاق والقيود والمرفقات؛ تثبيت مصدر baseline وcounts وhashes قبل التحويل.
2. تعيين مفاتيح المصدر والوجهة وقواعد normalization والمطابقة. صنّف duplicate exact/possible، orphan، missing/invalid، collision، والتعارضات؛ لا تدمج أو تحذف تلقائيًا بلا قاعدة يوافق عليها مالك البيانات.
3. نفّذ preview/dry-run على نسخة منقحة/معزولة: خرائط الحقول، سجل كل صف متوقع الاستيراد/التجاوز/الحجز، قواعد dedupe والسبب، counts قبل/بعد، عينات reconciliation؛ لا كتابة إلى production.
4. راجع الاستثناءات والملفات والصلاحيات ومراجعها؛ احصل على قرار مالك البيانات ومعالجة `OPEN-10` حيث تنطبق قيود الاحتفاظ/الوصول. شروط التنقية أو الحذف القانونية ليست محسومة هنا.
5. قبل cutover: عيّن window ومسؤول القرار، أوقف/جمّد تغييرات المصدر وفق خطة موثقة، احفظ snapshot قابلًا للاستعادة، سجل delta النهائي، وتحقق من الاختبار على نفس المحرك المعتمد.
6. نفذ import idempotent مع checkpoint/log آمن، ثم reconcile counts/hashes/references والقيود، journal/stock والملفات والتفويض. افتح الخدمة فقط بعد قبول فروقات موثقة ومراجعة smoke/authorization.
7. rollback: عرّف triggers والمالك مسبقًا؛ أوقف الكتابة/الحركة، احفظ أدلة الحالة، وارجع إلى snapshot/نسخة متوافقة أو نفذ forward-fix معتمدًا. لا تمحُ معاملات ما بعد cutover بصمت؛ احصرها وسوّها/عوضها بإجراء مصرح قبل reopening.

## 8. الصيانة والمراقبة والتشغيل

- يحدد المالك نافذة الصيانة، الإشعار والتصعيد، صاحب قرار الدخول/الفتح، ومدة التوقف المقبولة ضمن SLO. للنشر: اختبار staging، توافق schema بين الإصدارات، إيقاف استقبال تغييرات جديدة عند الحاجة، worker drain آمن، migration/health checks، ثم reopening بموافقة المشغل. لا تُجرى destructive migration بلا خطة recovery.
- سجّل ومراقب: availability وlatency/errors/throughput؛ DB connections/saturation/locks؛ queue age/depth/retries/DLQ/outbox lag؛ storage growth/failures/hash mismatch؛ آخر backup ونتيجة restore؛ upload quarantine؛ auth denials/session revocation؛ ونشر/maintenance/incident.
- structured logs/traces بمراجع correlation دون secrets أو PII؛ تنبيهات مع مالك استجابة ومسار تصعيد وrunbook. يحدد baseline والحدود الرقمية والاحتفاظ بعد قياس ومراجعة المالك، لا تُخترع thresholds في هذا brief.
